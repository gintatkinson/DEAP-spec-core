# Safety Engineering & Hazard Analysis Directory

This directory contains safety engineering artifacts, System-Theoretic Process Analysis (STPA) matrices, Failure Mode, Effects, and Criticality Analysis (FMECA) ratings, and SORA Specific Assurance and Integrity Level (SAIL) risk models for the Digital Engineering Agent Platform (DEAP).

## Purpose & Scope

The `docs/safety/` directory is the repository for safety assurance artifacts generated by Pipeline 0 Worker 0B (**STPA Hazard Analysis, FMECA & SORA SAIL Assurer**). Operating on the operational baseline established in `docs/conops/CONOPS.md`, Worker 0B executes rigorous hazard analysis, failure mode quantification, and risk mitigation mapping to establish formal safety constraints ($SC-1..N$) and Run-Time Assurance (RTA) switching requirements.

## Upstream Clean Landing Zone Invariant

In upstream distribution templates (`DEAP-*`), the `docs/safety/` directory is strictly maintained as a **clean landing zone** containing only `.gitkeep` and `README.md`. Concrete hazard analyses, STPA matrices, and SORA assurance artifacts (`STPA_MATRIX.md`) are never committed to upstream templates; they reside exclusively in downstream application workspaces initialized via `scripts/install_pipeline.sh`.

## Primary Commercial Toolchain Integration Context

This project explicitly declares **MATLAB / Simulink / Stateflow / Embedded Coder** as the Primary Tier-1 Commercial Toolchain Integration Context (Model-Based Design, Control Law Synthesis, DO-178C C/SPARK Ada code generation). Safety constraints ($SC-1..N$), Run-Time Assurance (RTA) monitors (ASTM F3269-17), and Unsafe Control Actions ($UCA-1..N$) formulated in `STPA_MATRIX.md` translate directly into formal Simulink Design Verifier (SLDV) proof invariants and Stateflow recovery supervisors.

## `STPA_MATRIX.md` Deliverable Specification

In downstream customer workspaces, Worker 0B generates `docs/safety/STPA_MATRIX.md` adhering to the following structural schema:

### 1. System Losses ($L-1..N$)
High-level unacceptable losses to stakeholders, people, or equipment (e.g. $L-1$: Loss of life or severe ground injury, $L-2$: Mid-air collision with crewed aircraft, $L-3$: Loss of aircraft or ground infrastructure).

### 2. System Hazards ($H-1..N$)
System states or conditions that, together with worst-case environmental conditions, lead to a system loss (e.g. $H-1$: Aircraft breaches containment geofence, $H-2$: Aircraft violates DAA well-clear safety separation).

### 3. Hierarchical Control Structure Topology
Textual and Mermaid architectural diagrams defining the control loops, controllers (RPIC, Autopilot, RTA Monitor), actuators, sensors, and communication channels.

### 4. Unsafe Control Actions ($UCA-1..N$)
Systematic identification of hazardous control actions across four failure modes:
1. *Not providing* causes hazard
2. *Providing* causes hazard
3. *Providing too early, too late, or out of order* causes hazard
4. *Stopped too soon or applied too long* causes hazard

### 5. Loss Scenarios ($LS-1..N$) & Causal Factors
Causal scenarios describing how UCAs occur (sensor degradation, actuator failure, data link drop, algorithm bug).

### 6. Formal Safety Constraints ($SC-1..N$)
Mandatory behavioral requirements and invariant boundaries that prevent UCAs (e.g. $SC-1$: Flight control system shall enforce pitch angle limits between $-15^\circ$ and $+25^\circ$).

### 7. FMECA Criticality Matrix
Component-level failure mode analysis detailing:
- Component Name & Subsystem
- Failure Mode & Local Effect
- System-Level End Effect
- Severity ($S$), Occurrence ($O$), Detection ($D$), and Risk Priority Number ($\text{RPN} = S \times O \times D$)
- Mitigating Design Control / Single Point of Failure (SPOF) elimination

### 8. SORA SAIL Risk Mitigations & OSO Traceability Table
- Determination of Final GRC and ARC
- SORA SAIL Classification (SAIL I through SAIL VI)
- Compliance matrix for mandatory Operational Safety Objectives (OSO-01 through OSO-24) at the required level of robustness (Low, Medium, High).

## KaTeX / LaTeX Mathematical Formatting Mandate

All markdown documents in this directory MUST strictly conform to KaTeX / LaTeX mathematical rendering requirements:
- Multi-line aligned equations MUST be enclosed in `\begin{aligned} ... \end{aligned}` within `$$` delimiters on dedicated lines.
- Bare alignment tabs `&` outside an alignment environment (`aligned`, `matrix`, `cases`) and `\begin{align*}` environments are strictly forbidden.
- Inline math expressions MUST be enclosed in single `$ ... $` delimiters.
